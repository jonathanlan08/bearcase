# AI trust boundary

## Model responsibilities
Classification (only when rules cannot decide), material-claim extraction with a source chunk index, evidence-role judgement for narrative claims, contradiction suggestions, unsupported-assumption identification, management-question and negotiation-condition drafting, narrative sections, explanation of persisted calculations.

## Deterministic code responsibilities
File validation and hashing; auth and per-deal authorization; state transitions; statement mapping; every financial formula and scenario; citation resolution; numeric claim verification with tolerances; add-back review rules; report validation; audit history.

## Rules enforced in code
1. Document text reaches the model only inside `<document>` tags with a system rule that it is data. Instruction-like text is flagged (`ingest/injection.py`), stored inert, and reported as a `document_integrity` finding.
2. Provider output must validate against `schemas/ai_v1.py` (`extra="forbid"`); invalid output is retried once, then recorded as `invalid_output` and the step degrades safely (claim dropped or routed to review).
3. A claim whose `source_chunk_index` does not resolve is discarded rather than persisted with an invented source.
4. Guardrails (`ai/guardrails.py`): Supported requires ≥1 supporting citation; Contradicted requires ≥1 contradicting citation; no citations → Unsupported; confidence < 0.6 or mixed evidence → Review required.
5. Numeric claims with an engine metric are decided by comparison in code (`pipeline/analyze.py::_compare`), never by the model. Tolerances: 1.0 percentage point, 2% for currency, 0.05 for multiples.
6. Only primary sources (statements, customer file, contracts, term sheet) can support or contradict; the seller's narrative documents never corroborate each other.
7. Original AI output is immutable. Human decisions are additive and audited.
8. Prompt version, schema version, model, provider, usage, and input hash are stored on every `ExtractionRun` and on every `Report`.
9. Missing evidence is stated, never invented. Absence of evidence yields Unsupported, not Contradicted.
10. Every demo surface discloses synthetic data and non-advice status.

## What a citation proves
A citation is an id that resolves to an evidence chunk or a persisted metric belonging to this deal. Resolving means the id exists, the row is owned by the deal, and the chip opens the source at its locator. That is provenance: the reader can see where a statement came from. It is not truth: no code checks that the cited source supports the sentence next to it. A claim, a report statement, or a chat reply can cite a real but unrelated row and pass every check in this file. The controls below make unsourced statements visible; they do not make sourced statements correct. Open the source.

Two things follow. The product never says a citation "verifies" a sentence; it says the citation was checked and asks the reviewer to read it. And the confidence shown on a claim is the extractor's confidence that the sentence is a material claim (or the rule score in mock mode), not a probability that the claim is true and not calibrated against outcomes; the guardrails use it only as a threshold for routing to review, and the status carries the judgement.

## What the add-back rules test
The add-back review (`engine`) is rule-based against statement lines: does the expense recur across the periods, does it exceed the prior year, is the line present at all. Those rules can accept an owner-compensation adjustment that is below the recorded owner salary without establishing a market replacement salary, and can accept a legal-cost adjustment on a year-over-year increase without matching it to a settlement. A rule's acceptance is a starting position, shown with its evidence; the reviewer's decision on each adjustment is the verification, and verified adjusted EBITDA is recomputed from those decisions.

## Ask the deal (chat)
The chat is a general assistant that also knows the deal. It answers any question directly (finance and M&A concepts, general knowledge, writing, code, casual conversation), in Markdown, and the trust boundary sits around deal facts rather than around the conversation as a whole. The model can only reach the deal through eight read-only tools over persisted rows (`chat/tools.py`: `list_claims`, `get_claim`, `get_financials`, `get_adjustments`, `get_scenarios`, `get_findings`, `search_evidence`, `get_evidence`). The system prompt (`chat/service.py`) requires that every deal fact come from a tool result and carry a `[E:<id>]`/`[M:<id>]` marker, and that every paragraph containing a figure (`$`, `%`, or a digit) carry a marker unless the figure sits inside a code block, with general explanations kept free of specific figures (otherwise they are shown as uncited); forbids calculating new deal numbers (persisted outputs are described, what-ifs are pointed to the Scenario Lab); requires "no evidence in the deal room" when that is the case; treats document text as untrusted data; forbids recommending buying, rejecting, or pricing the deal (explaining how an investor would weigh a risk is allowed); asks the model to lead with the direct answer in one or two sentences and then the supporting detail, with headings only for long answers; and requires general knowledge to read as general ("In general, ...") rather than as deal evidence. Rule 8 of the prompt is chosen by the deal (`chat/service.py::demo_note`): for the seeded demo (`deal.is_demo`) it says every number, company, and person is fictional and to say so if asked; for a deal a user created it says the documents are the user's own data, never to call them sample data, and never to invent a detail the tools did not return. Every live backend builds its prompt through `system_prompt(deal)`, never from the template directly. The rule-based composer (no key) keeps its deal-only behaviour and does not become a general assistant.

After the provider returns, code checks every citation marker, drops unresolvable ones, and sets the grounding flag. The grounding unit is the paragraph (blank-line separated): every paragraph that contains a figure (`$`, `%`, or a digit) must carry a resolved marker, and a reply that touched the deal (a tool ran, or a figure appears in the prose) must carry at least one resolved marker in total, so a deal answer with no citation at all is never marked grounded. Fenced code blocks and backtick spans are verbatim: markers inside them are shown literally and are neither resolved, rewritten, nor counted, and code is skipped when deciding whether a paragraph contains a figure. Heading lines (starting with `#`) and ordered-list markers (a leading `1.` or `1)`) are skipped for the same decision, so `## 3 risks` or `1. Owner salary` alone do not make a paragraph material. Code also assigns a scope to each reply: `general` only when no tool was called, no marker resolved, and the reply is grounded (no paragraph with an uncited figure); `deal` otherwise. A reply with an uncited figure is therefore never labelled general: it is flagged in the footer whatever its scope, and a general-scope reply is by construction free of uncited figures. The scope is stored inside the message's citations payload and sent to the client in the `citations` and `done` events. A general-scope reply is labelled as a general answer, is not treated as deal evidence, and never becomes a claim, a metric, or a report statement. These controls apply identically to Anthropic and to every OpenAI-compatible provider (OpenAI, Google Gemini, Groq, OpenRouter, Ollama, or a custom base URL). A provider adapter only transports messages; it cannot add tools, skip validation, clear the flag, or change the scope.

Order of events: text is streamed to the client as the provider produces it; the citation check runs when the reply is complete; the footer verdict (citation links checked, figures not cited, or general answer) arrives with the `done` event. Streamed text is therefore not prevalidated, and the panel does not describe it as such. The footer for a grounded deal reply says how many citations resolve ("All 4 citations resolve · review the answer") and asks the reader to review the answer; it does not say the reply is correct (see "What a citation proves"). Context handed into the chat from a page ("Ask about this claim" on a claim, "Ask" on an add-back) is plain user text: it enters the conversation exactly as if typed, with no markup, no citation markers, and no instructions to the model, and it is delivered once.

Interrupted replies: if the client disconnects while a reply is streaming, the text streamed so far is stored as the assistant message with the error "Stopped before the reply finished.", with the usual citation payload shape (evidence and metrics lists always present) and an audit row; nothing is streamed after the disconnect. The panel offers to regenerate it like any other last reply.

Model choice: `POST /api/deals/{id}/chat` accepts an optional `model` string. It is format-checked in code (`^[A-Za-z0-9][A-Za-z0-9._:/-]{0,79}$`; anything else is a 400) and, when the backend is live, must be one of the ids offered for the connected provider (the same list `chat/config` returns), otherwise a 400 with "Model is not offered for the connected provider."; only then does it replace the backend's model. The mock ignores it. The stored user and assistant rows record the model that actually answered. A listed id the provider has since retired produces the provider's error, mapped to an actionable message like any other provider error. `GET /api/deals/{id}/chat/config` lists the ids offered for the current provider in `models` (default first; `BEARCASE_CHAT_MODEL`, when set, is inserted first), and the same list is included in each connectable-provider entry.

Provider selection: `chat/providers.py` resolves the backend from `BEARCASE_CHAT_PROVIDER`. `auto` (the default) connects the first key found in the environment or `.env`, in the order anthropic, openai, gemini, groq, openrouter, ollama; `mock` keeps the chat offline whatever keys exist; a named provider without a working key falls back to the composer and says why in `chat/config`. Chat selection is independent of the extraction provider (`BEARCASE_AI_PROVIDER`). The panel header and the SSE `meta` event name the provider and model that answered, so a live model is never used silently.

Provider keys (`ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY`, `GEMINI_API_KEY` or its alias `GOOGLE_API_KEY`, `GROQ_API_KEY`, `OPENROUTER_API_KEY`, `BEARCASE_CHAT_API_KEY`, or their `BEARCASE_`-prefixed forms) are read from the process environment or the repo-root `.env` and nowhere else. A key is only ever sent to its own provider's endpoint, or to a gateway the operator names in `BEARCASE_CHAT_BASE_URL`; the `custom` provider uses `BEARCASE_CHAT_API_KEY` alone. No endpoint returns a key: `GET /api/deals/{id}/chat/config` reports the provider name, label, model, the `models` list, whether it is live, a plain-language note, the suggested questions, and the connectable providers (env var name, default model, model list, key URL, free-tier note); the SSE `meta` event carries `provider`, `model`, and `label`. Keys are never written to logs, audit rows, or chat messages, and provider error text is mapped to an actionable message with any key string redacted before it is streamed or stored.

No-tools fallback: when the selected model does not support tool calling, the chat runs a grounded single-shot mode instead. Code pre-fetches the same persisted rows the tools would return (claims, metrics, adjustments, scenario results, findings, evidence) and passes them to the model inside the user turn as delimited data, never in the system prompt, because evidence text is untrusted; the reply still uses `[E:…]`/`[M:…]` markers and goes through the same citation check, grounding flag, and scope assignment. In either mode the model sees nothing about the deal outside those rows and performs no calculation. The single-shot Q&A endpoint below shares the same rules.

Live providers have not been exercised end to end in this environment (no key is present); the tool loop, the fallback, error mapping, and key non-disclosure are covered by fake-client tests, and the guardrails above run in code regardless of provider. Prompt-injection resistance of a live model has not been measured; the injection fixtures run through the mock.

## Ask the Deal (single-shot Q&A endpoint)
Questions are answered only from persisted rows (claims, metrics, adjustments, scenario results, findings, evidence). Code builds the material and validates the answer; the model (or the rule-based composer) only drafts sentences. Sentences with numbers that lack a resolvable citation are removed and the answer is marked not fully grounded. No new calculations are performed while answering. The same limit applies: a resolving citation is provenance, not proof.

## Evaluations
`bearcase eval` seeds Northstar into a scratch database and scores: structured-output validity, extraction recall, status accuracy, contradiction precision, citation completeness, citation resolution, unsupported behaviour, review-required behaviour, no invented evidence, prompt-injection resistance, mock determinism, report citation validation, Ask the Deal grounding.

The evaluation runs on the curated Northstar fixtures with the mock provider. Passing it shows the pipeline still produces the expected result on those files; it is a regression check, not a measurement of extraction accuracy on unfamiliar documents or of a live model's behaviour. Measuring those needs an independently labelled set of unfamiliar deals and a real key.


## Corrections to mapped figures

A reviewer can correct a figure the mapper read from a statement. The correction is an additive row (`statement_corrections`) holding the original value, the corrected value, the reviewer, a note, and the recorded impact; the extracted metric row and the source cell are never edited. The pipeline applies the latest correction per line and period when it re-analyses the deal, marks the metric `corrected` with the mapper's value beside it, and the audit trail records the change. Undoing a correction is another correction back to the original, so the history stays complete.
